# 인앱 결제 관리 UI 감사 및 설계

2026-10-27 운영 화면 두 탭을 각각 캡처해 비교했다. 원본 캡처는 고객 데이터가 포함되어 저장소 밖 `/tmp/mindqna-purchase-audit-2026-10-27/`에 둔다.

## 발견 사항

| 영역 | 결제 내역 | 이용권 현황 | 영향 |
|---|---|---|---|
| 검색 | 유저 코드·내부 ID만, 검색 버튼 | 유저명·상품·결제 ID, 2자 이상 자동 검색 | 같은 값으로 탭을 바꾸면 결과가 이어지지 않음 |
| 조건 | 상태·플랫폼·환경·기간, 실패 단축 버튼 | 활성·유형·플랫폼·환경 | 유형·기간을 교차 조사할 수 없음 |
| 목록 | 플랫폼 → 유저, 구독 유형 없음 | 유저 → 플랫폼 → 유형 | 비교 시 열 위치와 정보 밀도가 달라짐 |
| 표시 | 복사 가능 ID, 상태 점 뱃지 | 복사 불가 ID, 일부 항목의 다른 형식 | ID 조사와 상태 판독의 학습 비용 증가 |
| 실제 데이터 | 실패 행의 플랫폼 값이 소문자 `ios` | 성공 행은 `IOS` | 동일 플랫폼인데 다른 텍스트·색상으로 표시됨 |

운영 브라우저에서 화면과 접근성 트리를 확인했다. 키보드 전용·스크린리더 실사용 검증은 코드 변경 후 별도로 확인한다.

## 결정

1. 두 탭 상단에 공통 검색·유형·플랫폼·환경·기간을 둔다. 검색은 유저 코드/내부 ID, 상품 ID, 결제 ID 한 칸에서 작동한다. Enter/검색 버튼으로 적용하고 초기화 및 적용 조건 칩을 제공한다.
2. 같은 검색·유형·플랫폼·환경·기간은 탭을 전환해도 유지한다. 상태는 데이터 의미가 달라 탭별 옵션을 유지한다(결제: 성공·실패·만료, 이용권: 활성·만료). 필터 위치와 조작 방식은 동일하다.
3. 두 표는 유저 → 플랫폼 → 유형 → 상품 ID → 결제 ID → 상태 → 환경 → 생성/구매 시간 순서로 맞춘다. 탭별로만 존재하는 완료 시간·만료일은 마지막 열이다. ID 복사, 날짜 형식, 상태/유형/환경 뱃지를 공통 컴포넌트로 표현한다.
   페이지당 행 수는 두 목록 모두 20개로 맞춘다.
4. 서버 `GET /admin/purchase`는 통합 `search`와 `isSubscribe`를 받고, 목록에 `isSubscribe`를 반환한다. 구독 판정은 결제 서버의 `isSubscriptionProduct` 규칙을 재사용한다. 기존 `username` 파라미터는 호환성 때문에 유지한다.
5. 서버 `GET /admin/products`는 내부 유저 ID 검색과 생성일 범위를 추가한다. 검색어는 1자부터 적용한다. 이용권도 실제 상품 처리의 `isSubscriptionProduct` 규칙으로 유형을 표시·필터한다. `dueAt`은 기간제 일반 이용권에도 있어 구독 판정에 쓰지 않는다. 비구독 유형의 UI 명칭은 `일반`으로 통일한다.

## 수용 기준

- 동일한 유저 코드/내부 ID, 상품 ID, 결제 ID를 각 탭에서 검색할 수 있다.
- 구독·일반, 플랫폼, 환경, 날짜 범위를 양쪽 탭에서 조합할 수 있다.
- 탭 전환 시 공통 조건이 보존되고 적용 조건을 한 개씩 제거하거나 전체 초기화할 수 있다.
- 상태는 각 데이터의 의미를 유지하고 같은 점 뱃지 체계를 쓴다.
- 소문자/대문자 플랫폼 값은 동일한 표시로 정규화한다.
- 기존 API 호출과 페이지네이션을 깨지 않으며, 서버·어드민 검사와 수동 화면 검증을 통과한다.
