# 푸시 대상 필터 — 설계

- 날짜: 2026-08-26
- 범위: `mindqna-server` (조건 해석·분할 저장), `mindqna-admin` (조건 입력·목록 접기)
- 선행 문서: `2026-08-20-admin-push-redesign-design.md`

## 1. 문제

지금 전체 발송은 `User.locale` 하나로만 대상을 좁힌다. 운영팀은 그보다 좁게 보내야 할 때가 있다 — 커플 공간을 쓰는 사람, 질문을 열 개 이상 받은 공간, 펫을 키운 공간.

요청받은 조건은 넷이다.

| 조건 | 데이터 위치 |
|---|---|
| 공간 유형 | `SpaceInfo.type` — couple / family / friends / alone |
| 공간 언어 | `SpaceInfo.locale` |
| 질문 개수 | `Card` — 아래 §4 참조 |
| 펫 레벨 | `Pet.level` |

넷 다 **공간**의 속성인데 푸시는 **사용자**에게 간다. 둘은 `Profile`로 이어진다.

## 2. 결정된 의미

**한 공간이 모든 조건을 동시에 충족해야 한다.** 사용자는 공간을 최대 5개까지 갖는다. "커플 + 펫레벨 10"은 커플이면서 동시에 펫레벨 10인 공간 하나를 뜻하지, 커플 공간 하나와 별도의 레벨 10 공간을 합친 것이 아니다. 쿼리에서는 모든 조건을 같은 `Profile` 조인 행에 매달아 보장한다.

**공간 언어와 계정 언어는 다르다.** 기존 `locale` 필터는 `User.locale`, 즉 앱 언어다. 새 `공간 언어`는 `SpaceInfo.locale`이다. 앱이 한국어인 사용자가 영어 공간을 가질 수 있으므로 둘은 서로 다른 질문에 답한다. 둘 다 유지하고, 둘 다 지정되면 둘 다 적용한다.

**필터는 전체 발송에만 붙는다.** 개인 발송은 이미 수신자를 이름으로 지정하므로 조건이 좁힐 것이 없다.

## 3. 구조 — 조건이 아니라 결과를 저장한다

조건을 푸시 행에 저장하고 발송기가 매 배치 다시 푸는 방식을 먼저 만들었다가 폐기했다. 폐기 이유는 둘이다.

- 조건마다 컬럼이 필요해 다섯 번째 조건이 생기면 마이그레이션이 따라온다.
- 저장된 것이 "대상이 무엇으로 정의됐는가"일 뿐이라, 나중에 **누가 실제로 받았는지 알 수 없다.** 조건은 날마다 다른 사람 집합으로 풀린다.

채택한 구조는 이렇다.

```
조건 입력 → 저장 시점에 한 번 해석 → 사용자 이름 목록
         → 1,000명씩 분할 → AdminPush 행 N개 생성 (같은 groupId)
         → 발송기는 각 행을 평범한 개인 발송으로 처리
```

**발송기는 한 줄도 바뀌지 않는다.** 상태 흐름, 배치, 재시도, 재개, 중단 규칙 모두 그대로다. 캠페인이라는 개념을 발송기가 알 필요가 없다.

대상이 저장 시점에 확정된다는 부작용이 있다. 예약 캠페인이라면 나가는 순간이 아니라 승인한 순간의 대상이 간다는 뜻인데, 이쪽이 맞다 — 승인한 것이 나간다.

### 분할 단위와 상한

- `PUSH_CHUNK_SIZE = 1000` — `userNames` 컬럼이 이미 강제하는 `MAX_USER_NAMES`와 같은 값.
- `PUSH_FILTER_MAX_RESULTS = 50000` — 캠페인 하나의 천장. 1,000명씩이면 50행이고, 목록이 접을 수 있고 취소가 훑을 수 있는 한계다. 이보다 넓게 잡히는 조건은 의도한 조건이 아닐 가능성이 높다.
- 조회는 천장보다 하나 더 요청한다. "정확히 상한"과 "상한 초과"를 구분해야 거부 메시지가 정확해진다.

## 4. 질문 개수 — `Card.order` 준조인

`Card.order`는 발급 시 `totalCards + 1`로 매겨진다(`card.service.ts:179`). 따라서 **공간의 최대 order가 곧 카드 수**다.

처음에 `MAX(order) >= N`으로 썼다. 옳지만 느리다 — MAX는 훑는 공간마다 값을 계산한다. `EXISTS (… AND order >= N)`은 필터가 실제로 묻는 약한 질문이라 첫 행에서 멈추고, `idx_card_space_order`가 seek로 답한다.

dev 실측, 같은 결과 집합 기준:

| 조건 | MAX | EXISTS |
|---|---|---|
| 질문≥10 (245,881명) | 40.3초 | 9.8초 |
| 커플+ko+질문10+펫5 (16,500명) | 4.1초 | 0.7초 |

`Space.cardOrder`는 쓰지 않는다. 이름이 비슷하지만 템플릿 시퀀스 포인터이고(`card.service.ts:287`이 `template.order`를 그대로 넣는다), 로케일·공간유형으로 건너뛴 템플릿이 있으면 실제 카드 수보다 크다.

## 5. 성능 — 필요한 인덱스는 하나

저장 경로 쿼리를 dev에서 재니 10~25초가 나왔다. 조건 해석이 동기 HTTP 요청 안으로 들어왔으므로 그대로면 저장이 타임아웃난다.

`EXPLAIN`이 원인을 특정했다.

```
tbl=si   type=ALL     key=null                       rows=291,311  Using where; Using temporary; Using filesort
tbl=pt   type=eq_ref  key=PRIMARY                    rows=1
tbl=p    type=ref     key=Profile_spaceId_userId_key rows=2
tbl=u    type=eq_ref  key=PRIMARY                    rows=1
tbl=c    type=ref     key=idx_card_space_order       rows=16       Using index
```

`SpaceInfo` 전체 스캔이 병목이고 나머지는 전부 인덱스로 1~16행씩 짚는다.

같은 계획이 **`idx_pet_level`이 쓸모없다는 것도 보여준다.** `Pet`은 `spaceId`로 조인돼 `eq_ref`로 1행씩 잡히므로 `level` 인덱스를 탈 일이 없다. 초안에 넣었던 것을 근거 없이 제안했던 것으로 판단해 뺀다.

### 인덱스만으로는 부족했다 — 조인 순서를 고정한다

인덱스를 적용하고 재측정하니 22.0초가 18.0초가 됐을 뿐이었다. `EXPLAIN`을 다시 보니 계획이 **바뀌기만 했다.**

```
tbl=p    type=ALL     key=null   rows=558,548   ← Profile 전체 스캔으로 옮겨감
tbl=si   type=eq_ref  key=PRIMARY  rows=1
```

`SpaceInfo` 조회가 싸지자 옵티마이저가 구동 테이블을 `Profile`로 바꿨는데, `Profile`이 581,549행으로 `SpaceInfo`(295,535행)보다 크다.

원인은 추정치다. `(type, locale)` 인덱스의 조합은 27개지만 행 추정은 **첫 컬럼만으로** 나온다 — 295,535/4 ≈ 75,102이고 실제 매칭은 37,702이다. `SpaceInfo` 경로가 실제의 두 배로 계산돼 진다.

`STRAIGHT_JOIN`으로 `SpaceInfo`를 구동 테이블로 고정한 결과:

| 조건 | 인덱스 전 | 인덱스만 | +조인 고정 |
|---|---|---|---|
| 커플+ko+질문10+펫5 (16,517명) | 22.0초 | 18.0초 | **0.6초** |
| 커플만 (상한 초과) | 10.4초 | 8.2초 | **2.4초** |
| 질문≥10 (상한 초과) | 24.8초 | 23.3초 | 16.5초 |

미리보기 카운트는 같은 조건에서 0.4초다.

느린 마지막 경우는 `SpaceInfo`에 조건이 없어 좁혀지지 않는 케이스인데, 245,881명이 잡혀 **어차피 5만 상한에 걸려 거부된다.** 저장에 성공하는 경로는 0.6초다.

힌트를 쓰는 것이 통계에 거는 도박이 아닌 이유: 조건이 없어도 `SpaceInfo`가 `Profile`보다 작으므로 `SpaceInfo` 선행이 더 나쁠 경우가 이 쿼리에는 없다. 그리고 prod 통계는 dev와 다르다 — 옵티마이저 추정에 5배가 걸려 있는 것을 그대로 두지 않는다.

비동기 해석(§11)은 필요 없어졌다.

## 6. DDL (수기 적용)

```sql
ALTER TABLE `AdminPush`
  ADD COLUMN `groupId` VARCHAR(191) NULL COMMENT '같은 조건으로 쪼개진 발송 묶음';

CREATE INDEX `idx_adminpush_group` ON `AdminPush` (`groupId`);
CREATE INDEX `idx_spaceinfo_type_locale` ON `SpaceInfo` (`type`, `locale`);
```

컬럼은 `groupId` 하나뿐이고 nullable이다. 기존 단건 발송은 `NULL`이라 아무 영향이 없다.

`idx_adminpush_group`은 그룹 취소가 `updateMany({ where: { groupId } })`로 돌기 때문에 둔다. `AdminPush`는 작은 테이블이라 이득이 크지 않지만 비용도 없다.

## 7. 서버

### 새 파일 — `src/admin/push/push-target-filter.ts`

- `PushTargetFilter` 타입. 모든 필드 선택적이고, 빠진 필드는 조건 자체가 빠진다.
- `countMatchingUsers(filter, userLocale)` — 작성 화면 추정치용.
- `selectMatchingUserNames(filter, userLocale, limit)` — 저장 시 해석용. `DISTINCT`가 두 공간으로 매칭된 사용자의 중복 발송을 막는다.
- `chunk(items, size)` — 분할. 자체 테스트를 갖는다. 여기서 off-by-one이 나면 캠페인 꼬리가 조용히 사라지고, 증상이 "일부가 못 받았다"로 보여 버그로 안 읽힌다.

Prisma 쿼리 빌더는 관계 개수로 필터할 수 없어 raw SQL을 쓴다.

### `PushService`

- `previewTargets(filter, locale)` — 개수만 반환. 이름 목록은 저장 때 다시 푼다. 여기서 목록을 돌려주면 실제 발송분과 어긋날 수 있는 사본이 하나 더 생긴다.

  두 쿼리는 같은 `whereClause`를 지나므로 **조건은 항상 일치한다.** 다만 작성과 저장 사이에 데이터가 바뀌면 **개수는 달라질 수 있다** — 그 사이 펫 레벨이 오른 공간은 미리보기에 없었지만 저장분에는 들어온다. 이는 결함이 아니라 두 시점 사이의 실제 변화이고, 미리보기를 `isApproximate: true`로 표시하는 이유다. 저장 결과는 `N개로 나뉘어 등록` 토스트가 실제 행 수로 알려주므로, 운영자가 최종 규모를 확인할 자리는 미리보기가 아니라 목록이다.
- `createFilteredPush(dto, filter)` — 해석 → 분할 → 한 트랜잭션으로 행 생성.
  - `buildData`를 청크마다 **먼저 전부** 돌린다. 아니면 9개 행을 만든 뒤 10번째에서 거부되는 상황이 생긴다.
  - `$transaction`에는 **미실행 프라미스**를 넘긴다. `Promise.all`로 먼저 await 하면 트랜잭션 밖에서 실행돼, 실패 시 절반만 저장된 캠페인이 남는다.
- `cancelPush(id)` — 행에 `groupId`가 있으면 그룹 전체에 적용한다. 대기 중은 `CANCELED`, 진행 중은 `ABORTED`. 한 청크만 멈추면 다음 청크가 1분 뒤 시작하므로 아무것도 막지 못한다.

### 에러

| 코드 | 뜻 |
|---|---|
| `PUSH_FILTER_NO_MATCH` | 조건에 맞는 사용자 없음 |
| `PUSH_FILTER_TOO_MANY` | 상한 초과. `max`를 함께 반환 |

### API

- `POST /admin/push/preview-targets` — 조건 → `{ count, isApproximate, max }`
- `POST /admin/push` — `filter`가 있으면 캠페인 생성. **반환이 배열로 바뀐다** — 단건도 길이 1의 배열이라 호출부가 분기하지 않는다.

## 8. 어드민

### 조건 패널 — `PushTargetFilterPanel`

전체 발송 아래에 `대상 조건` 섹션. 공간 유형·공간 언어는 다중 선택 칩, 질문 개수·펫 레벨은 임계값 입력.

빈 입력은 `undefined`로 파싱한다. `Number('')`는 0이고, "질문 0개 이상"은 실제 조건이므로 미지정과 혼동하면 좁은 캠페인이 전체 발송으로 넓어진다.

공간 언어 행의 힌트가 계정 언어와 다르다는 것을 명시한다. 비슷한 이름의 두 필드를 나란히 두고 운영자가 알아서 구분하기를 기대하지 않는다.

### 대상 수

조건이 있으면 `previewTargets`, 없으면 기존 `getPushTargetCount`. 조건이 있는데 기존 것을 쓰면 로케일 전체(약 44.5만)를 세어 16,500명짜리 캠페인 옆에 표시되고, 확인 다이얼로그가 틀린 숫자를 인용한다.

### 목록 접기 — `push-grouping.ts`

16,500명 캠페인은 17행이다. 그대로 두면 한 페이지가 캠페인 하나로 차고 17개의 별개 발송으로 읽힌다.

- 같은 `groupId`를 한 항목으로 접고 제목에 `3/17` 배지를 붙인다.
- 숫자는 **합산**한다. 첫 행에서 읽으면 17,000명 캠페인의 발송 수가 1,000으로 나오는데, 그 숫자로 운영자가 성공 여부를 판단한다.
- 상태는 전체를 설명하는 것을 고른다. 움직이는 것이 끝난 것보다 우선한다 — 세 청크가 끝나고 하나가 발송 중일 때 `발송 완료`로 보이면 아직 멈출 수 있는데 없다고 말하는 셈이다. 같은 이유로 `FAILED`가 `CANCELED`보다 우선한다.
- `finishedAt`은 모든 청크가 가질 때까지 `null`이다.
- 항목은 가장 이른 청크의 자리를 유지한다. 아니면 청크 상태가 바뀔 때마다 캠페인이 표에서 튀어다닌다.

### 저장 후

`N개로 나뉘어 등록되었습니다`. 이 말이 없으면 목록의 배지를 보고 중복 저장으로 오해한다.

## 10. 확인하지 못한 것

**화면을 보지 못했다.** 브라우저 확장이 연결되지 않아 조건 칩, 목록 접기, `3/17` 배지의 실제 렌더를 확인하지 못했다. 코드·타입·테스트는 통과했고 쿼리는 dev DB에 직접 돌려 검증했다.

**인덱스 적용 후 재측정이 남았다.** §5의 진단은 `EXPLAIN`에 근거하지만, 적용 후 실제 저장이 몇 초인지는 측정해야 한다. 이것이 구현 계획의 첫 검증 항목이다.

**실기기 발송을 해본 적이 없다.** 이는 이 기능이 아니라 푸시 재작업 전체에 걸린 미결 항목이다.

## 11. 하지 않기로 한 것

**필터 컬럼 4개.** §3의 이유로 폐기. 커밋 `c51af71`에 구현됐다가 `88b82dc`로 되돌렸다.

**수신자 조인 테이블.** 해석 결과를 별도 테이블에 넣는 안. `userNames`가 이미 같은 일을 하고 발송기가 이미 읽으므로 새 테이블은 저장소만 하나 더 늘린다.

**비동기 해석.** 저장을 즉시 반환하고 백그라운드에서 대상을 푸는 안. 22초의 원인이 누락된 인덱스 하나로 판명돼(§5) 불필요해졌다. 인덱스 적용 후에도 느리면 이 안으로 돌아온다.

**`idx_pet_level`.** 초안에 넣었다가 `EXPLAIN`이 무용함을 보여 제외(§5).

**예약 시점 재해석.** 예약 캠페인이 나가는 순간의 조건으로 대상을 다시 잡는 안. 승인한 것과 나가는 것이 달라지므로 채택하지 않았다.
