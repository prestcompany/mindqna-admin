# 책 발주 주문 행별 처리

## 처리 기준

- 주문번호가 같아도 주문서의 각 행을 독립된 발주 항목으로 취급한다.
- 주문번호 원문과 각 행의 수량을 보존한다. 수량만큼 행을 복제하지 않는다. 예: 동일 주문번호의 브라운 2권, 핑크 1권은 수량이 각각 2, 1인 두 항목이다.
- 이전의 주문번호별 옵션 행 합치기는 제거한다. 각 행에 해당 책의 옵션이 있어야 한다.
- 질문 범위의 최소·최대 문항 수 제한은 없다.

## 구현

- 서버 파서는 비어 있지 않은 주문번호가 있는 행마다 주문을 생성한다. 업로드 500건 제한은 행 수 기준이다.
- 서버 답변 통계는 주문번호 대신 입력 배열의 위치로 연결한다. 같은 주문번호의 서로 다른 공간·범위가 섞이지 않아야 한다.
- 발주 요청의 주문번호 중복 검사를 제거한다. DB 항목의 기본 키 id를 유지하고 `(batchId, orderNo)` 유니크 인덱스를 일반 인덱스로 변경한다.
- 어드민은 업로드 결과에 고유 행 키를 부여한다. 선택·결제 질문 수 선택·필터·확정은 이 키를 사용한다.
- 상세 목록도 각 항목을 별도 행으로 표시한다. 미리보기는 요청 내용이 바뀌면 초기화한다.
- 수량은 업로드 목록·상세·미리보기에 표시하고, 확정 요청·DB 스냅샷·재다운로드·제본소 JSON의 `quantity`로 전달한다. 기존 저장 항목과 수량 필드가 없는 구버전 요청은 1로 처리한다. 명시적인 잘못된 수량은 거부한다.
- ZIP은 같은 이름이 이미 있으면 `_2`, `_3` 순서로 충돌 없는 이름을 배정한다. 정규화한 파일명의 충돌과 여러 다운로드 청크 간 충돌도 방지한다. JSON 안의 주문번호는 바꾸지 않는다.

## 검증 및 적용

- 동일 주문번호의 다른 옵션·공간·범위를 가진 행과 완전히 동일한 행이 모두 유지되는지 테스트한다.
- 행별 선택 및 결제 질문 수 변경이 다른 행에 영향을 주지 않는지 검증한다.
- 발주 저장 및 재다운로드 시 동일 주문번호 항목이 모두 남는지 검증한다.
- SQL은 담당자가 서버 배포 전에 직접 적용한다. Prisma migrate나 운영 DB 변경은 에이전트가 실행하지 않는다.
- 이미 합쳐서 저장된 과거 발주는 복원되지 않는다. 원본 주문서를 다시 업로드해야 한다.
