# 공통 펫 간식 등록 수정 계획

**목표:** 간식을 특정 진화 타입에 연결하지 않고 등록·수정할 수 있게 하고, 경험치 0.5 입력과 사슴·돼지 선택지 제거를 실제 간식 사용 및 진화까지 검증한다.

**범위 결론: 어드민과 서버 모두 수정·배포가 필요하다.** 어드민만 고치면 공통 간식 이력만 있는 펫의 다음 진화 타입 조회가 실패하며, 이미 등록된 간식의 타입을 지우는 API 요청도 현재 계약에 맞지 않는다. DB 마이그레이션은 필요 없다. `PetSnack.type`과 `PetMeta.type`은 nullable이고, 경험치는 Float다 (`mindqna-server/prisma/schema.prisma:189-215`).

## 요구사항 해석과 현재 동작

- **공통 간식**은 `PetSnack.type = null`인 간식이다. 모든 간식은 이미 펫 타입 제한 없이 조회·사용할 수 있다 (`mindqna-server/src/pet/pet.service.ts:53-78`). 이번 변경은 사용 대상 확대가 아니라 진화 타입을 지정하지 않고 저장하는 것이다.
- 간식 경험치는 타입과 관계없이 `snack.exp`가 그대로 펫 경험치에 더해진다 (`pet.service.ts:104-115`). `type`은 별도 이력에 기록되며, **normal** 간식의 타입 있는 이력만 진화 타입 결정에 쓰인다 (`pet.service.ts:110-115,464-466,659-666`). **special** 간식도 경험치는 주지만 현재 진화 타입 집계에는 포함되지 않는다. 이 규칙은 유지한다.
- 새 간식 폼의 현재 경험치 기본 표시값은 0이지만 서버가 이를 0.5로 저장한다. 서버에서 명시적 0을 보존하게 되면 **폼 기본값도 0.5로 변경**해 미수정 신규 등록의 기존 저장 결과를 유지한다. 운영자가 직접 입력한 0은 0으로 저장한다.
- 이미 등록된 간식은 어드민 목록에 저장된 간식 항목이다. 타입을 지정했던 항목을 공통으로 바꿀 수 있어야 한다. 과거에 먹인 이력(`PetMeta`)은 그 시점의 기록이므로 간식 정의를 수정해도 소급 변경하지 않는다.
- 서버 코드 기준 진화 가능한 타입은 강아지·고양이·토끼·다람쥐·햄스터·펭귄·병아리·곰의 8종이다 (`pet.service.ts:462,656`). 사슴·돼지는 Prisma enum과 공통 어드민 목록에는 있지만 간식의 진화 선택지에서 제외한다.

## 구현 작업

### 1. 서버: 진화 타입 선택을 한 경로로 통일

**수정:** `mindqna-server/src/pet/pet.service.ts`  
**추가:** `mindqna-server/src/pet/pet-evolution-type.ts`, `src/pet/pet-evolution-type.spec.ts`  
**기존 테스트 확장:** `mindqna-server/src/pet/pet.service.spec.ts`

1. 순수 함수의 실패 테스트를 먼저 작성한다. 입력은 normal 간식 이력의 `type`, `createdAt`, `spaceId`; 출력은 유효 8종 중 하나다.
2. 유효 타입만 집계하고, 횟수 내림차순 → 마지막 섭취 시각 내림차순 → 고정 타입 순서로 동률을 결정한다. `null` 및 사슴·돼지 이력은 집계에서 제외한다.
3. 집계가 비면 `spaceId`에 기반한 안정적인 대체 타입을 고른다. 이는 현재의 호출마다 달라질 수 있는 랜덤 대체를 **의도적으로** 바꾸는 정책이다. 같은 공간에서 이력이 변하지 않았다면 반복 미리보기와 실제 진화의 결과가 일치해야 한다.
4. `getNextPetType()`과 `confirmPetType()`이 이 함수를 함께 사용하게 한다. 두 DB 조회의 `action: 'snack'` 필터는 유지한다.
5. 테스트: 이력 0건, 공통 간식만, 공통+타입 혼합, 사슴·돼지만, 유효 타입 여러 개(다수 타입 우선), 횟수 동률(최근 타입 우선), 같은 공간의 반복 미리보기와 레벨 13 실제 진화 결과 일치를 검증한다. `type: null`인 간식도 경험치가 0.5 증가하고 이력 타입이 `null`로 기록되는지 확인한다. `evolution()` 반환값은 타입 확정 전 객체일 수 있으므로 실제 타입은 후속 조회로 검증한다.

### 2. 서버: 명시적 공통 타입 및 경험치 저장

**수정:** `mindqna-server/src/admin/admin.dto.ts`, `src/admin/pet/types/pet.types.ts`, `src/admin/pet/pet.service.ts`  
**테스트:** `mindqna-server/src/admin/pet/pet.service.spec.ts` 및 개발 환경의 실제 HTTP 요청

1. 생성·수정 요청의 `type`을 `PetType | null`로 허용한다. 수정 시 `type: null`은 DB 값을 지우고, 필드 미전달은 기존 동작대로 유지한다. 실제 `POST /admin/snack`, `PUT /admin/snack/:id`가 JSON `null`을 수용하는지 API 수준에서 확인한다.
2. `exp || SNACK_EXP_DEFAULT`를 `exp ?? SNACK_EXP_DEFAULT`로 바꿔 명시적 0과 0.5를 입력 그대로 저장한다. 생성과 수정 각각 테스트한다. 폼에서 경험치를 건드리지 않은 신규 등록은 0.5를 보내 기존 저장 결과를 유지한다.
3. 생성→조회→수정→조회에서 `type: null`과 `exp: 0.5`가 유지되는지 검증한다. 스키마·enum·과거 이력 데이터는 변경하지 않는다.

### 3. 어드민: 공통 선택과 소수 경험치

**수정:** `src/components/page/snack/SnackForm.tsx`, `src/components/page/snack/SnackList.tsx`, `src/client/types.ts`

1. 폼에 명시적 `공통(진화 타입 지정 안 함)` 라디오를 추가한다. UI 내부에서는 문자열 값으로 다루고 저장 요청에서만 `null`로 변환한다. 새 간식의 기본 선택은 공통으로 한다. 타입 있는 간식 수정 시 현재 선택은 유지한다.
2. `PET_TYPE_OPTIONS`를 간식 폼에서만 유효 8종으로 제한한다. 공통 상수 및 서버 enum의 사슴·돼지는 다른 도메인에서 쓰일 수 있으므로 제거하지 않는다. 이전 데이터에 사슴·돼지가 있으면 수정 화면에서 현재 값을 알리고 공통 또는 유효 타입으로 **재선택하기 전에는 폼 제출을 막는다**. 그대로 저장하려는 경우의 실패 검증을 추가한다.
3. 새 간식의 경험치 기본값을 0.5로 바꾸고 입력에 `min=0`, `step=0.5`를 적용한다. 값을 건드리지 않은 신규 등록 및 명시적 `0`, `0.5`, `1`, `1.5`의 입력·제출을 확인한다.
4. API 요청/응답 타입의 `type`을 nullable로 맞추고 목록의 `null`을 `공통`으로 표시한다. 폼의 변경 값을 재조회했을 때 유지되는지 확인한다.
5. 공통 간식도 경험치는 지급하고, 진화 타입별 섭취 횟수에는 포함되지 않는다는 설명을 표시한다.

## 검증 및 배포

1. **서버 테스트:** `yarn test --runInBand src/pet/pet-evolution-type.spec.ts src/pet/pet.service.spec.ts src/admin/pet/pet.service.spec.ts`, `yarn build`, 수정 파일 대상 ESLint. 서버 `yarn lint`는 자동 수정 명령이므로 다른 파일까지 바뀌지 않게 결과를 점검한다.
2. **어드민 검사:** `npx tsc --noEmit`, `pnpm lint`. 순수 로직을 추출했다면 `pnpm test`. 개발 환경에서 폼과 API 왕복을 확인한다.
3. **운영 데이터 읽기 전용 점검:** 이미 저장된 `PetSnack.type`, `PetMeta.type`, `Pet.type`에서 사슴·돼지 건수를 확인한다. 이미 진화한 펫 데이터 수정 여부는 별도 결정한다. 자동 데이터 변경은 이 작업에 포함하지 않는다.
4. **서버를 먼저 배포:** 공통 간식 이력 조회와 `null` 수정 요청을 수용할 준비를 한 뒤 어드민을 배포한다. DB 마이그레이션은 없다.
5. **개발 환경 스모크 테스트:** 경험치를 건드리지 않은 공통 간식 신규 등록(`exp=0.5`) → 목록/재조회 확인 → 타입 있는 간식을 공통으로 수정 → 앱에서 공통 간식 먹이기(경험치 +0.5) → `GET /pet/evolution/type` 정상 반환 → 레벨 13 진화 후 **후속 GET/DB 조회**로 타입 일치 확인. 기존 타입 지정 간식의 등록·사용도 재확인한다.
6. 개발 환경 통과 후 운영 배포 및 같은 경로의 최소 스모크 테스트를 진행한다.

## 완료 기준

- 새 간식과 이미 등록된 간식에 `type: null`을 저장·재조회할 수 있다. 펫타입 선택은 공통 + 유효 8종이며 사슴·돼지는 간식 선택지에 없다.
- `exp=0.5`가 브라우저 폼, API, DB, 실제 펫 경험치까지 0.5로 유지된다. `exp=0`도 입력값 그대로 저장된다.
- 공통 간식은 모든 펫에게 노출·사용 가능하고 normal 간식의 일일 사용 횟수에 포함된다. 진화 타입별 집계에는 포함되지 않는다.
- 공통 간식만 먹었거나 사슴·돼지 이력만 있는 펫의 진화 타입 조회와 실제 진화가 오류 없이 유효 8종을 선택한다.
- 간식 이력이 변하지 않은 경우 진화 타입 미리보기와 실제 최종 진화 타입이 같다.
- 서버·어드민 검증 명령과 개발 환경 API/화면 스모크 테스트가 통과한다.

## 계획 리뷰 반영 (2026-10-26)

- 리뷰에서 서버 `||`→`??` 변경만 하면 새 간식의 미수정 경험치가 0이 되는 회귀를 지적했다. 폼 기본값 0.5와 미수정 등록 검증을 추가했다.
- 레벨 13 진화 API의 반환 객체가 타입 확정 전 값일 수 있음을 반영해 후속 조회로 실제 타입을 검증한다.
- 사슴·돼지 레거시 간식은 재선택을 폼 검증으로 강제한다.
- 안정적 대체 타입은 현재 랜덤 정책 변경임을 명시하고 반복 조회 테스트를 추가했다.
